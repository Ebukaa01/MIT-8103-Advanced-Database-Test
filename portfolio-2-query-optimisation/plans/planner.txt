--- [B3] Planner Decision Analysis ---
Metric                 | Chosen Index Scan     | Forced Seq Scan       | Variance / Ratio
-----------------------+-----------------------+-----------------------+------------------
Estimated Total Cost   | 82.14                 | 5823.54               | 70.9x lower cost
Actual Execution Time  | 0.349 ms              | 48.401 ms             | 138.7x faster
Shared Buffer Hits     | 8 pages               | 4 pages               | +4 pages
Shared Buffer Reads    | 0 pages               | 1,862 pages (~14.6MB) | -100% disk reads
Rows Scanned (Ledger)  | 50 rows (early exit)  | 400,000 rows          | 8,000x fewer rows
Sort Node              | Eliminated            | Top-N Heapsort (31kB) | Sort bypassed

Why the Planner Decided for Index Scan:
1. Ordering: `idx_ledger_account_created` stores keys physically ordered by `(account_id, created_at DESC)`.
   Because the index already matches the query's `ORDER BY l.created_at DESC`, the explicit Sort node is eliminated.
2. LIMIT Pushdown: With an ordered index scan, the executor terminates immediately after fetching 50 rows.
   Under Seq Scan, all 400,000 rows must be inspected and sorted before top 50 can be returned.
3. Cost Model Check: Cost estimate (82.14) is vastly below the sequential scan threshold (5823.54),
   proving the optimizer accurately predicts the superiority of the index path.

--- [C3] Selectivity & Cost Analysis ---
Metric                 | Index Only Scan       | Forced Seq Scan       | Variance / Ratio
-----------------------+-----------------------+-----------------------+------------------
Estimated Total Cost   | 182.39                | 6892.21               | 37.8x lower cost
Actual Execution Time  | 1.134 ms              | 54.946 ms             | 48.5x faster
Heap Pages Visited     | 0 (Heap Fetches: 0)   | 1,130 pages           | 100% heap bypass
Shared Buffer Hits     | 41 pages              | 2 pages               | Pure cache hit
Shared Buffer Reads    | 0 pages               | 1,130 pages (~8.8MB)  | -100% disk I/O
Rows Evaluated         | 14,003 qualifying     | 200,098 scanned       | 93% rows pruned

Why Index Only Scan Wins at 7% Selectivity:
- The partial predicate `WHERE txn_type = 'TRANSFER' AND status = 'COMPLETED'` reduces the index to only 14,003 rows (48 pages vs 1,130 table pages).
- `INCLUDE (amount)` embeds the aggregation payload inside index leaf tuples.
- Because `VACUUM (ANALYZE)` flagged all heap blocks as all-visible in the visibility map, `Heap Fetches = 0`.
- The planner's estimated cost of 182 reflects scanning 48 index pages versus reading 1,130 table pages + evaluating 200,000 CPU filter tuples (cost 6892).


========================================================================
PART D: SELECTIVITY DECIDES (THE SELECTIVITY TIPPING POINT)
========================================================================

Experiment Setup:
  Transactional test on table `customers` (1,000 rows).
  Predicate status values:
    - 'SUSPENDED' :   10 rows (~1.0% selectivity -- rare)
    - 'ACTIVE'    :  990 rows (~99.0% selectivity -- common)

Execution Script:
  BEGIN;
  CREATE INDEX tmp_customers_status ON customers (status);
  ANALYZE customers;

--- [D1] Rare Predicate: status = 'SUSPENDED' (~1% Selectivity) ---

EXPLAIN (ANALYZE) SELECT * FROM customers WHERE status = 'SUSPENDED';

                                                          QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on customers  (cost=4.29..14.32 rows=10 width=148) (actual time=0.021..0.028 rows=10 loops=1)
   Recheck Cond: (status = 'SUSPENDED'::customer_status)
   Heap Blocks: exact=2
   ->  Bitmap Index Scan on tmp_customers_status  (cost=0.00..4.29 rows=10 width=0) (actual time=0.012..0.012 rows=10 loops=1)
         Index Cond: (status = 'SUSPENDED'::customer_status)
 Planning Time: 0.148 ms
 Execution Time: 0.042 ms


--- [D2] Common Predicate: status = 'ACTIVE' (~99% Selectivity) ---

EXPLAIN (ANALYZE) SELECT * FROM customers WHERE status = 'ACTIVE';

                                                    QUERY PLAN
-------------------------------------------------------------------------------------------------------------------
 Seq Scan on customers  (cost=0.00..23.50 rows=990 width=148) (actual time=0.008..0.182 rows=990 loops=1)
   Filter: (status = 'ACTIVE'::customer_status)
   Rows Removed by Filter: 10
 Planning Time: 0.081 ms
 Execution Time: 0.221 ms

ROLLBACK;
ANALYZE customers;


--- [D3] The Tipping Point Explanation ---
Observation:
- Even though `tmp_customers_status` exists and indexes column `status`, the planner
  ACTIVELY IGNORES the index when querying `status = 'ACTIVE'` and prefers a `Seq Scan`!
- For `status = 'SUSPENDED'`, the planner selects `Bitmap Index Scan`.

Cost Modeling Mathematics:
- PostgreSQL calculates total cost based on estimated page I/O and tuple processing:
  Cost(SeqScan)   = (Pages * seq_page_cost) + (Tuples * cpu_tuple_cost)
                  = (12 * 1.0) + (1000 * 0.01) + (1000 * 0.0025) ≈ 23.50
  Cost(IndexScan) = (IndexPages * random_page_cost) + (SelectedRows * random_page_cost) + CPU
                  For 990 rows: (2 * 4.0) + (990 * 4.0) + CPU ≈ 3,968.00!

Conclusion:
When row selectivity exceeds the "tipping point" (typically ~5% to 15% depending on table density
and `random_page_cost`), reading scattered heap pages via random I/O becomes vastly more expensive
than streaming the entire relation sequentially. The query optimizer correctly detects this and
switches execution strategies dynamically based on catalog statistics.
